# 要不要接 Gopeed 当下载引擎（2026-10-24 评估）

> 触发：用户发现 [GopeedLab/gopeed](https://github.com/GopeedLab/gopeed)，问「也许可以整合到我们的插件中」，
> 同时带来另一份方案（P0 多连接 / P1 续传 / P2 自适应并发 / P3 统一任务状态）。
> 这份文件只回答两件事：**接不接 Gopeed**、**那四条按什么顺序做**。

## 结论

1. **现在不接。** 不是因为接不了，是因为它解决的问题不是我们当前的瓶颈。
2. **P0~P3 吸收，但顺序改成 P1 → P0 → P2 → P3'**（P3 要改写，见下文）。
3. **Gopeed 记成 S6 之后的可选引擎**，触发条件只有一个：BT / magnet / ed2k 变成真需求。

## 一、事实（可查的部分）

| 项 | 事实 |
|---|---|
| 许可证 | **GPL-3.0** |
| 规模 | 27.1k star，Go 内核 + Flutter 界面，仓库 ~14.7 MB |
| 协议 | HTTP/HTTPS（多连接）、BitTorrent、magnet、ed2k |
| 驱动方式 | REST API（TCP，默认 `127.0.0.1:9999` + 可设 token）、CLI 单二进制（`go install …/cmd/gopeed`）、JS SDK `@gopeed/rest`、社区 Python SDK `gospeed_api`、2.0 起还有 MCP 端点 |
| 附赠 | 自带浏览器扩展、JS 站点扩展、webhook、下载后脚本 |

**许可证这一关要说清楚，不要拿它当挡箭牌**：GPL-3.0 只在「链接 / 派生」时传染。我们要走的是
**独立二进制 + 子进程 + 本地 API**，这与仓库里已经在做的 ffmpeg 完全同一种模式
（`bin/ffmpeg.exe` 162 MB 就躺在包里，也是 GPL 系构建）。所以法律上可行，义务是随包提供
上游源码获取方式 + 不改名不暗示背书。**真正的问题不是法律，是下面三件事。**

## 二、为什么不接（三条，都不是"体积大"）

顺带纠一个直觉：包里已经有 323 MB 的 ffmpeg/ffprobe，再加一个几十 MB 的 gopeed
**在体积上根本不是问题**。所以别用体积当理由。

1. **它不解决用户的抱怨。** 用户最近三次的原话是「这几条有什么区别、该点哪个」、
   「退出界面后没有下载记录」、「下载下来应该是标题而不是哈希」。这三件事全部落在
   L0 会话契约 / L1 读响应体 / L2 验证这层 —— Gopeed 一行都不解决。接它之后，
   用户依然面对两行一模一样的「HLS 流（视频）」，只是下得更快（如果它真的更快的话）。
2. **失败文案是我们的产品语言，交出去就没了。** 我们卖的是「下不下来时告诉你为什么」
   —— 12 个错误码、`host_phase` 阶段文案、段级重试计数，都是按这句话写的。
   Gopeed 的失败信息是它自己的模型，我们只能在外面再包一层翻译，等于多一层失真。
3. **多一个进程就是多一类支持工单。** 端口占用、防火墙弹窗、杀软拦截、用户手动关了它、
   开机没起来 —— 每一条都会变成「插件坏了」。ffmpeg 是**按需短命进程**（下完即退），
   Gopeed 是**常驻服务**（要活着等任务），风险等级不同。

## 三、它真正值钱的地方（将来要接就为这个）

- **BT / magnet / ed2k**：这三个自己写永远不划算。如果产品路线里出现「磁力链」需求，
  Gopeed 是唯一现实选项，且必须走旁挂进程，不能内嵌。
- **`resolve_task`（先解析资源→再建任务）**：这正是我们 L2 规划表要做的事，
  它把「URL → 资源描述 → 任务」这条路走通了，值得当参考读一遍，别重复造。
- **任务模型（pause / continue / retry / 重启恢复）**：S4 工作站可以借鉴它的状态字段划分。

## 四、P0~P3 逐条判断

先确认那份表的事实基础：**它说 `run_urllib()` 是单流，属实。**
我核过 `native-host/downloader.py`：`Range` 只在**续传时**出现过（`bytes=<已有长度>-`），
没有分段并发。这条批评成立，不用辩护。

### P1 「续传前校验 ETag/Last-Modified」→ **排第一，比提速重要**

现在的 `.part` 只认**长度**。如果这期间服务端换了内容（重新转码、CDN 换切片、签名 URL 换批次），
长度对得上就照续 —— **拼出来的是坏文件，而 ffprobe 往往还能打开**，于是我们的验证层
会放它过去。这是"错并且不自知"，比慢一百倍都严重。

做法：`.part` 旁边存 `ETag` + `Last-Modified` + `Content-Length` 三元组指纹。
**任一变化就作废 `.part` 整单重下**，不试图续 —— 续错的代价远大于重下的时间。

### P0 「多连接 Range」→ **已量，结论：暂不做（1.06×）**

2026-10-24 实测（`tools/throughput_check.py`，同一文件同一时刻，各 3 轮取中位数，
只量前 32 MB 以保证两边下的是同样字节）：

```
源：github.com/GopeedLab/gopeed/releases/download/v1.9.3/…android.apk（70.7 MB，支持 Range）
单连接：10.1 / 9.8 / 10.6 MB/s   中位数 10.1 MB/s
4 连接：11.2 / 10.7 / 10.7 MB/s  中位数 10.7 MB/s
倍数 1.06×  →  判据 ≥2× 才算值得，**不达标**
```

10 MB/s ≈ 80 Mbps，正好是本机出口带宽 —— 说明**瓶颈在链路，不在「少开了几个连接」**。
这 400 行并发分片代码省下来是对的。

副产物两条，都很重要：

1. **测速过程中 4 连接那一轮直接吃了 `HTTP 429`**（`proof.ovh.net`，单连接两轮都正常）。
   这不是巧合：不少 CDN/网盘对「同一 IP 多连接」就是限速或拒绝。**多连接在会被限速的站上
   是负收益**，而恰好是这些站才需要它。
2. 所以 **P2（自适应降级）比 P0 更值钱**：与其加速，不如先把「被限速时怎么退」写对。

**什么时候重新评估**：换到「单连接被服务端限速」的场景（网盘直链、某些 CDN 边缘节点限速），
或者用户报「同一个文件用别的下载器快十倍」。届时先跑一次本工具，再谈写不写。

### （原始判断保留）P0 原本定为「排第二，先量再写」

单流确实是事实，但"该提速"和"提速值得写 400 行"是两件事。先做测量：
同一个真实 mp4（几十 MB 级），1 连接 vs 4 连接的实测吞吐，记下倍数。倍数不到 2×
就先不做 —— 那说明瓶颈在对端而不是我们。

真做的时候三条约束：
- 分片写**独立临时文件**，最后按序合并；不要边下边 `seek` 写同一文件（杀软扫描 + NTFS 随机写会吃掉收益）。
- **必须保留单流回退**：不支持 `Range`、签名 URL 只允许一次请求、429 限速，都退回单流。
- 分片数按 `Content-Length` 算，不按"固定 4 段" —— 20 MB 切 4 段每段才 5 MB，握手开销比省下的还多。

### P2 「自适应降级」→ **排第三，且必须挂在已有错误码上**

降并发 / 退单流这个动作本身没错，但"自适应"这个词容易写成黑箱。我们的口径是：
403/429/超时各归哪个错误码、重试几次、第几次开始降并发、降到底之后给用户看哪句话 ——
**全部落进已有的 12 错误码表**，不新建一套状态。默默降级到用户看不出发生了什么，
等于把"告诉你为什么"这句产品承诺又还回去了。

### P3 「统一任务状态与完整性校验」→ **方向要改写**

表里写的是"避免 HTTP、HLS、yt-dlp 三条路径产生不一致的状态"，听起来要新造一层统一状态机。
**不需要。** 我们已经有单一状态文件（`jobs/<id>.json` + `<id>.cancel`），并且
`host_phase_test` / `host_status_race_test` / `host_validation_test` 三套测试在守它。

真正缺的不是"统一状态"，是**三条路径的失败判定各有一套**：
yt-dlp 会假失败（退出码 0、真文件已好、尾部一行 ERROR）、HLS 有段级重试、
HTTP 有瞬时抖动。所以 P3 应该改写成：

> **P3'：把三条路径的失败判定收敛到同一张错误码表**，同一类原因在三条路径上
> 给出同一个码、同一句人话。

### 表里「HLS 分片并发已有线程池和顺序写盘」→ 属实，**别动**

`run_hls_self` 确实是线程池 + 按序写盘，且 `host_segment_retry_test`（20 秒那套）
专门守着段级重试。这条在 P0 改造里要明确划出去，不要顺手"统一"掉。

## 五、最终建议

| 动作 | 什么时候 |
|---|---|
| P1 续传指纹校验 | ✅ 1.3.47 已做 |
| P0 多连接 + 单流回退 | ⛔ 实测 1.06×，**不做**；条件见 §4-P0 |
| P2 自适应降级（落进错误码表） | **升到下一步**（429 是真实风险，P0 不做反而更该做） |
| P3' 三路径失败判定收敛 | 与 S2（验证四层 + 错误码）合并做 |
| 旁挂 Gopeed 引擎 | S6 之后；**唯一触发条件：BT/magnet 成真需求** |

一句话记住判断标准：**我们卖的不是"下得快"，是"下对了"。提速是加分项，坏文件是减分项 ——
加分项可以晚点做，减分项不能。**
