## 现象

保存媒体时文件建不出来（Windows 文件名 255 字符上限），或者文件名带着尾随的
点和空格（系统建文件时把扩展名一起剥掉，得到一个没有后缀的文件）；中文标题
前的全角空格（`　`）洗一次还留着，重下同一条时名字对不上。

## 复现

- 喂一个扩展名本身超长的标题：`sanitize("a." + "b" * 300)` → 返回 301 字符；
- 喂 `"\u3000.PRN.webm"`（全角空格开头）→ 洗一次原样返回，洗两次才干净；
- 喂 `"x" * 149 + " .mp4"` 给 `sniffer_host._safe_name` → 结果以空格结尾。

## 根因

三个独立缺陷，全在「名字进磁盘前」的最后一道函数里：

1. 截断公式 `root[:100 - len(ext)] + ext` 在扩展名本身超长时 `100 - len(ext)`
   是负数，负切片直接失效，长度完全不受控；
2. 两套「空白」定义不一致：`str.strip()` 认全部 Unicode 空白（含 U+3000），
   而 `.strip(" .")` 只认 ASCII 空格和点 —— 后者从左边剥点时撞到全角空格就停，
   于是「首尾空白」和「首尾点」两层清洗互相留尾巴；
3. `_safe_name`（宿主侧）是另一份独立实现，`name[:150]` 截断做在
   `strip(". ")` **之后**，第 150 个字符恰好是点或空格时留下脏尾。

## 修复

- 抽出 `_strip_edges()` 统一空白判据（`isspace() or == "."`），并在截断**之后**
  再洗一次（截断本身可能制造新的脏尾）；
- `_safe_name` 把截断提前到 strip 之前，`rstrip(". ")`，并补上空值与 Windows
  保留名复查；
- 两份实现（`downloader.sanitize` 与 `sniffer_host._safe_name`）在
  `test/sanitize_test.py` 的 [5] 段对同一批边界用例跑，防止再分叉。

这批缺陷是变异测试（`tools/fuzz_host.py`，断言不变量而非正确答案）挖出来的，
单测一条都没覆盖——谁也没想过「扩展名能有 300 个字符」。
