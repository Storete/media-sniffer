# compatibility 规则库（L4 知识库的人工通道）

> 这是 PRODUCT-PLAN §4「L4 知识库双通道」里**人工进**的那一条。
> 另一条（解释库：同站+同码累计 ≥3 次自动出建议）在 `native-host/knowledge.py`，
> 由系统自动记账，不经过本目录。
>
> **为什么这条通道必须有人守门**：解释库学错的代价只是「解释不准」；
> 规则库错一条，用户会**下错文件且不自知**（把封面当正文、把广告当内容）。
> 代价不对称，所以准入要三件齐全，每条启用规则必须有测试钉着。

## 收什么、不收什么

**该学的是「失败模式」，不是「站点规则」。**

- ✅ 收：「封面/装饰图混进正文图片」「带 BOM 的清单首行被当成地址」这类
  可穷举、十年后仍成立的失败模式，以及由此产生的**判定规则修订**。
- ❌ 不收：「XX 站该走哪条链」的硬编码站点表（站点无限且会变）、
  「我开发时踩的坑」（那是 DEVLOG 的事，见 HANDOFF 文档的甄别原则）。

每条案例入库前先问：**这是「用户会撞见的失败」，还是「我自己开发时的坑」？**
后者写 DEVLOG，不占这里的坑位。

## 准入三件套

三条**缺一不可**，凑不齐就不许新增条目：

1. **用户报告**：有人真的撞见了（真机记录、用户反馈）；
2. **根因**：代码层面的因果说得清（「可能是网络问题」不算）；
3. **可复现测试**：`test/` 里有至少一条测试钉住这个修复——CI 会查它真的存在。

## 文件规范

- 命名 `NNN-slug.md`，编号递增，如 `001-sanitize-filename-boundary.md`；
- 复制 `000-template.md` 起步（该文件是样板，门禁豁免它，**新案例不许再叫这个名字**）；
- frontmatter 四个机器字段 + 正文四个人话小节，见模板。

### frontmatter 字段

| 字段 | 说明 |
|---|---|
| `id` | 与文件名同名（不含 `.md`），方便 CI 报错时定位 |
| `状态` | 只有 `已启用` / `已停用` 两个值；停用要写明原因（正文末尾加「## 停用」小节） |
| `测试引用` | 空格分隔的一个或多个 `test/xxx_test.py` / `test/xxx.test.js`；**必须真实存在** |
| `适用版本` | 修复从哪个版本起生效，如 `1.3.42` |

### CI 门禁（`tools/check_compat_rules.py`）

判据是 PRODUCT-PLAN 原话：「**每条启用规则必须有测试引用**」。本地跑：

```
python tools/check_compat_rules.py
```

规则：凡是 `状态: 已启用` 的案例，「测试引用」必须解析出至少一个路径、
每个路径都指向 `test/` 下**真实存在**的文件；缺字段、缺正文小节、引用的文件
不存在、状态写了别的值，一律红。目录里一条案例都没有时**绿**
（空库不卡提交，但也打一行提示）。

> 反向验证教训（d-052/d-058：假绿比真红更危险）：门禁不能只查「文件里有『测试』
> 两个字」，必须解析出具体路径并确认存在；门禁本身被
> `test/compat_gate_test.py` 钉着（无引用/坏引用/缺字段必须红，空库必须绿）。
