## 一、S5 是什么、做到哪了

L4「知识库双通道」分两条腿，代价不对称（PRODUCT-PLAN §4 原话）：

| 通道 | 谁写 | 触发 | 错了的代价 | 当前状态 |
|---|---|---|---|---|
| **解释库**（自动长） | 系统 | 同站+同码累计 ≥3 次 → popup 出「已知问题+建议」 | 只是解释不准，**不会下错文件**，所以敢自动 | ✅ **全部落地**（1.3.55/1.3.56） |
| **规则库**（人工进） | 人 | 用户报告 + 根因 + 可复现测试三件齐全才准入 | 错一条让用户**下错且不自知**，所以必须有人守门 | ⬜ **未做**（本文的活） |

**核心原则（别做反了）**：该学的是「失败模式」，不是「站点规则」。
失败模式十来个可穷举且十年后仍成立；站点规则无限且会变。
所以规则库收的是**可复现的失败案例 + 判定规则的修订**，不是「XX 站该走哪条链」的硬编码表。

## 二、要交付的三样东西

### 1. `docs/compatibility/` 目录 + 模板（目前不存在，要新建）

PRODUCT-PLAN 定的模板字段：

```
现象 / 复现 / 根因 / 修复 / 测试引用 / 适用版本
```

文件命名 `NNN-slug.md`（如 `001-segment-gap.md`）。

**关键：模板不是空壳，是「判定规则变更」的入库单。** 每条案例必须能回答：
- 现象：用户看到什么（一句人话）
- 复现：怎么稳定复现（URL/操作/环境）
- 根因：为什么错（代码层面的因果，不是「可能是网络问题」）
- 修复：改了哪个函数、怎么改的
- 测试引用：指向 `test/` 里哪条测试钉住了这个修复
- 适用版本：从哪个版本起生效

### 2. 规则库 CI 卡门（改 `.github/workflows/tests.yml`）

判据是 PRODUCT-PLAN 原话：「**每条启用规则必须有测试引用**」。

落地形态（建议）：CI 里加一步，扫描 `docs/compatibility/*.md`，凡是标记「已启用」的案例，
必须能解析出**一个非空的「测试引用」字段**；解析失败或引用为空 → 红。

要避免的坑（本仓库 d-052/d-058 的教训：**假绿比真红更危险**）：
- 不能只检查「文件里有『测试』两个字」，要解析出**具体的测试文件名**并确认它在 `test/` 里存在。
- 反向验证这条 CI 门禁本身：故意写一条「测试引用指向不存在的文件」的案例，CI 必须红。

### 3. 回填原料（把 DEVLOG 里的真实案例转成 compatibility 条目）

原料已经在流水账里，只是没归类。优先回填这些（每条都已「有现象+根因+修复+测试」四件齐全，只需转录）：

| 原料 | 失败模式 | 说明 |
|---|---|---|
| DEVLOG d-047 | 超长扩展名 / 全角空格不幂等 / BOM 首行 / 尾随脏字符 | 变异测试挖出的边界缺陷，已修 |
| DEVLOG d-052 | 测试替身假跑（`.cmd` 被 shell 拆管道） | 是「怎么测」的教训，不一定是用户可见失败模式，酌情收 |
| DEVLOG d-054 | 错误码断链（err 不转发） | 诊断链路，不是站点失败 |
| DEVLOG d-055 | 三条路径同因不同话 | 收敛到码表 |
| DEVLOG d-058 | 会话缺 images / NaN!==NaN / 沙箱缺 URL | 数据模型缺陷 |
| DEVELOPMENT B6~B11 | Telegram 分组 / 焦点收窄 / 封面误收 | 站点级「判定规则」的真实案例 |

> 注意甄别：**不是每条 DEVLOG 都该进 compatibility**。compatibility 收的是「会反复踩的
> **失败模式**」，不是「我写过的一行代码」。像 d-052 那种「测试脚手架怎么搭」是内部工程笔记，
> 不该占 compatibility 的坑位。回填时先问：这条是「用户会撞见的失败」还是「我自己开发时的坑」？

## 三、为什么不现在做完（给接手者的上下文）

1. **规则库靠「三件齐全」驱动，不是靠排期驱动。** 它的输入是真实用户报告 + 根因 + 可复现测试，
   这三样现在没有攒够（真机验证还卡在 T-E5，ffmpeg 起不来）。硬塞案例 = 造假的规则库。
2. **CI 卡门和模板可以先立**（不依赖真机、纯逻辑），但「往里填案例」必须等真实失败攒够。
   所以接手顺序建议是：**先立模板 + 立 CI 卡门（空库也能跑绿），再随真机失败逐条回填。**

## 四、接手时的落地顺序（建议）

1. 建 `docs/compatibility/`，写 `README.md`（说明模板字段 + 准入三件套）+ 一个 `000-template.md` 样板。
2. 改 `.github/workflows/tests.yml`，加「规则库测试引用」门禁步骤（纯脚本，不依赖网络）。
3. 门禁脚本先反向验证：空库跑绿、伪造无引用/坏引用跑红。
4. 从 DEVLOG 里挑「用户可见失败模式」逐条转录，每条带真实测试引用。
5. 全部绿后，升版本号、写 DEVLOG 条目、更新 TODO 的 T-C7 行状态。

## 五、验收判据（怎么算做完）

- `docs/compatibility/` 有模板 + 至少一条真实案例（带非空、真实存在的测试引用）。
- CI 里「规则库测试引用」门禁存在，且**反向验证过**（坏引用必红）。
- 空库状态 CI 也能绿（门禁不因「还没案例」就红——那会卡死所有提交）。
- TODO 的 T-C7 行「待做」里的「规则库（人工通道）+ compatibility 模板 + CI」三项划掉，状态可考虑转 ✅（档位：自动化通过，案例真实度待真机）。
