# 国内高频站审计（2026-10-23）

**目的**：不是「适配这些站」，而是量清楚两件事 —— ①扩展在真实用户每天打开的站上抓得对不对；②抓得不对的，**到底是扩展的缺陷，还是站点本来就没有可下载内容**。

**方法**：Chrome 156 + 未登录（游客态）+ 独立 profile，逐站打开首页、等 13 秒、读扩展后台 state 与 popup 实际视图，两轮各 19 站。
样本按 MAU 量级取，不是「支持清单」——`video` 为 0 的站并不是抓不到，而是首页本来就没有正在播放的视频。

## 三、缺陷与修法

四类噪声的共同点：**特征全在 URL 里，而旧的 `looksLikeIcon()` 只看 DOM 上下文**（hint / w / h），webRequest-only 的条目这三样全空。

| 类型 | 实例 | 旧逻辑为什么放过 |
|---|---|---|
| 图标名自证 | 高德 `_next/static/media/satellite-icon.png` 21506B、快手 `ks-web/web-app-logo.png` 9238B | 24KB 线以下，且不检查 URL 里的 icon/logo |
| 埋点像素 | 芒果 `apm.log.mgtv.com/s.gif`、百度 `sp1.baidu.com/…/v.gif?logactid=` | `.gif` 不在 `.svg|.ico` 规则里，CDN_HINT 也不含这些域 |
| 构建产物 | `/_next/static/media/`（Next.js 打包素材） | `isSiteUiAsset` 只认 `svg-next/`、`archive/` 目录 |
| 极小体积 | 支付宝 648B、芒果 638B/693B | 尺寸判据要靠 DOM 的 w/h，裸条目拿不到 |

### 已实施（1.3.40）

在 `background.js` 新增 4 条 URL 判据，**排在 24KB 体积线之前**（d-020 的坑：47KB 素材被体积线抢先放行）：

```js
UI_NAME_URL      // 文件名里带 icon|logo|sprite|favicon|avatar|badge|placeholder|loading|btn…
UI_NAME_GLUED    // 拼音拼接：wenxinlogo_
UI_DIR_PATH      // /controlbar/ /toolbar/ /navbar/ /skin/ /theme(s)/
TRACKER_URL      // 统计子域、/s.gif /v.gif、?logactid=、fourier 的 /ts
BUILD_ASSET_DIR  // /_next/static/media/ /static/media/
TINY_IMAGE       // 2KB 以下且无标题
```

**为什么敢放在体积线之前**：真封面一个都不命中 —— B 站 `bfs/archive/<hash>.jpg@672w`、快手 `p*.yximgs.com/upic/…`、淘宝 `…_360x360`、小红书 `…/spectrum/1040g…!`。

### 真机验证（Chrome 156，改后复测）

| 站 | 图（改前→改后） | 说明 |
|---|---|---|
| 高德 | 7 → **0** | 7 张全是 `_next/static/media/` 图标，全清 |
| 百度 | 4 → **2** | logo 与 `v.gif` 埋点清掉 |
| 快手 | 4 → **3** | `web-app-logo.png` 清掉，3 张视频封面保留 |
| 芒果TV | 58 → **41** | 埋点、下载按钮、close.png 清掉；剩余见下 |
| 小红书 | 45 → **51** | 内容图未误杀（数量波动来自信息流不同） |
| B站 | 28 → **21** | 封面未误杀 |

单元测试 `test/icon_filter.test.js` **20 项**（A 素材命名 7 / B 埋点 3 / C 构建产物 1 / D 极小体积 3 / E 误杀回归 5），先红 15 条再转绿；Node 12 套全绿。

## 四、已知局限（**有意不做**）

1. **芒果 TV 剩余 41 张**：全是 `vipcdn.mgtv.com/upload4/mgtv_cashier/` 下的抽奖/支付弹窗背景（`LotteryDialog`、`red_pack_top`、`bg_light` 169KB）。
   再加一条 `dialog|popup|modal` 规则就能清掉，但那是**逐站适配的起点**，每加一条都在抬高误杀面。芒果本身是 DRM 站，不在支持范围 —— 停在这里。
2. **京东 142 张商品图**：页面确实有这么多图，扩展如实反映是**正确行为**。用户不想看，属于使用场景问题，不该靠过滤解决。
3. **首页 `video` 为 0 的站**（B站/小红书/腾讯视频）：封面瀑布流，点进详情页才有播放器。这不是抓不到，是没在播。

## 五、对「适配大部分网站」这个说法的修正

按字面理解这是无限任务（yt-dlp 有 1800 个 extractor、20 多人在天天修）。审计给出的实际结构是：

| 类型 | 覆盖情况 | 代表 |
|---|---|---|
| A 标准 HTTP 流（mp4/m3u8/直链） | ✅ 已能 | 51cg1、4kvm、微博、今日头条 |
| B MSE / DASH 分片 | ⚠️ 能录「播过的部分」 | 抖音、Telegram（已修）、爱奇艺预览 |
| C DRM | ❌ 不该做 | 腾讯视频、爱奇艺、优酷、芒果 |
| D 登录墙 | ❌ 技术无解 | 91rb 游客态 |
| E 伪装/加密分片 | ✅ 已解决 | 4kvm（PNG 壳）、51cg1（AES-128） |

**A + E 覆盖绝大多数站，C + D 不该也不用覆盖，剩下的只有 B —— 而 B 每站都要单独写，写不完。**
所以收口标准不是「支持多少站」，而是 **「A 类成功率做实 + B/C/D 的失败说得清」**。
