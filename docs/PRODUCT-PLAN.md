# 产品化方案：从「下载扩展」到「本地媒体工作站」

> 状态：提案 v1（2026-10-24）
> 前置阅读：`DEVELOPMENT.md`（现状与待办）、`AGENTS.md`（开发纪律）、`docs/site-coverage.md`（实测覆盖度）
> 本文不改任何代码，只定方向、切边界、给验收标准。
> **每层的验收判据见 [`docs/ACCEPTANCE.md`](ACCEPTANCE.md)** —— 本文只写「这一层要达成什么」，
> 那里写「怎么算真的达成了、证据长什么样、什么情况一票否决」。

---

## 1. 先说三个会让产品死掉的陷阱

产品化不是把功能堆到 40 个。这一类别里死掉的扩展，死因高度集中：

| 死因 | 表现 | 本项目当前风险 |
|---|---|---|
| **商店政策** | 被下架、被要求移除功能 | 中。不含 DRM 绕过的声明、不出现 YouTube 示例，基本可过 |
| **维护跑步机** | 站点改版 → 规则失效 → 逐个救火 → 三个月后放弃 | **高**。B6~B11 六条已完成的修复全是站点特判 |
| **失败无解释** | 用户说「下不了」，你说「我这边好的」 | **高**。有 `msRecentErrors` 但无分类码，无法归因 |

第二条和第三条是同一个病：**系统对自己为什么成功、为什么失败都没有结构化认识**。产品化的全部技术工作，本质上是在补这个认识。

---

## 2. 一句话定位（差异化必须能被复述）

> **它不帮你找到 200 个能下的站；它保证你下下来的那一个是对的，下不下来时告诉你为什么。**

前半句是「不做覆盖度军备竞赛」，后半句是「做正确性与可解释性」。理由很硬：

- 覆盖面你已经量过了（34 站首页 + 9 站深链 + 12 详情页），**再翻一倍也不会变成护城河**——竞品（猫抓、Video DownloadHelper、FetchV）都在同一水位。
- 但「下下来没声音」「只有前 30 秒」「花屏」「合并没有对齐」是这一类别**普遍的翻车点**，因为大家都不做输出验证。
- 而「为什么不行」几乎没人做，因为它需要在架构里预留证据链——**这是唯一能靠设计领先、且抄不走的地方**。

---

## 3. 架构判断：扩展变薄，本地引擎变厚

这是本项目已有、但**没有用足**的结构性优势：`native-host/` 已经是 Native Messaging 宿主，竞品大多只有一个扩展。

| | 只有扩展的竞品 | 本项目应有形态 |
|---|---|---|
| 标签页关掉 | 下载中断 | 引擎继续跑 |
| 大文件 | 扩展内存受限（当前页面侧 `MAX_MSE_TOTAL=512MB` 已顶到） | 落盘流式，无上限 |
| 批量/队列 | 做不了 | 天然 |
| 历史/库 | 无 | 本地库 + 检索 |
| 崩溃排查 | 只能问用户 | 引擎有日志与诊断包 |

**结论**：扩展只做三件事——采集证据、发起任务、显示状态。解析、规划、下载、验证、归因、记账，全部下沉到本地引擎。

## 4. 五层重构（按依赖顺序，不可跳）

### L0 · 数据契约：把「条目袋」换成「会话」

现状：`rec.items` 是一个标签页一袋扁平条目，靠去重/编号/过滤让用户在里面认人。

目标：**会话（Session）是一等公民**。

```js
{
  sid: "bilibili:BV1xx:1690...",     // 站点 + 页面身份 + 会话起点，稳定、可去重
  site: "bilibili.com",
  page: { url, title, referer },
  kind: "video" | "audio" | "image-set",
  tracks: [
    { role: "video", variants: [ { id, height, codec, bitrate, url, size, manifestId } ] },
    { role: "audio", variants: [ { id, codec, bitrate, url, size } ] }
  ],
  manifest: { type: "hls"|"dash"|"file", duration, segments, initUrl },
  subs: [ { lang, url, format } ],
  cover: url,
  evidence: [ { src: "dom"|"net"|"mse"|"manifest", field, value } ],
  confidence: "strong" | "weak" | "conflict",     // 离散等级，不用小数
  state: "discovered"|"planned"|"running"|"verifying"|"done"|"failed",
  error: { code, stage, hint, retriable }
}
```

**为什么它是地基**：清晰度选择要在 `variants` 上挂，双轨配齐要在 `tracks` 上挂，验证要在 `manifest.duration` 上挂，归因要在 `error.code` 上挂。没有这一层，后面四层全是空中楼阁。

**验收**：新模型与旧 `items` **双跑并行**，同一页面上两条路径产出等价结果（差异只允许是新增字段）；否则不许切流。

### L1 · 采集升级：从「监听地址」到「读内容」

现状（已核实）：

- `inject-main.js:1826-1868` 已劫 `addSourceBuffer` / `appendBuffer`，**MSE 原始字节已经抓到了**（128MB/条、512MB 总量、30 分钟 TTL）。这条路已经走完。
- `fetch` hook（1772-1789）与 `XHR` hook（1799-1817）**只取 `content-type` / `content-length`，从不读响应体**。
- 全文唯一 `resp.json()` 在 2643 行 `biliFetchPlayurl()` —— 它主动请求 B 站 playurl，写死 `qn=64, fnval=16, fourk=1`，拿回 DASH 双轨 + 全清晰度。
- `清晰度 / quality / variant` 在 `popup.js`、`background.js` 中出现 **0 次**。

**判断**：`biliFetchPlayurl` 是这件事的反证——读 API 响应体完全可行，只是**一个站一个站地手工写**。泛化它就是产品化的核心增量。

分两级，风险不同，不能一把梭：

| 级别 | 读什么 | 约束 | 收益 |
|---|---|---|---|
| **L1-a** | 已判定为媒体的响应体（m3u8 / mpd） | 单响应 ≤256KB，只留文本 | 清晰度变体、分片数、时长、init 段预检 |
| **L1-b** | 播放器 API 类 JSON 响应 | 只扫 http(s) 地址、**不落盘**、单响应截 64KB、**独立开关默认关** | DASH 双轨自动成对、私有 JSON 清单（腾讯正片/抖音）从放弃变可解 |

**工程硬约束**（每条都是踩过的坑）：

- 一律 `resp.clone()` 读体，**绝不能吃掉原始流**，否则页面自己坏。
- 读体失败必须静默（`catch {}`），不影响页面任何行为。
- 大响应走 `reader` 流式截断，不要 `await resp.text()` 之后才截。
- 页面被 Service Worker 接管时 hook 看不到 → 必须有 fallback（`webRequest` 只有 URL，退回现有逻辑，不得报错）。

**验收**：一个真实 m3u8 站点，popup 里出现 ≥2 档清晰度且能选中；关掉开关后行为与今天完全一致（可回归）。

### L2 · 引擎升级：规划表 + 输出验证

**L2-a 规划表外置**。现在 5 条下载链（直链分块 / HLS / yt-dlp / MSE 落盘 / 伪装分片）的分派散落在各处 `if` 里，连你自己都难说清「这条为什么走了 yt-dlp」。

```js
planDownload(session) -> {
  chain: "chunked" | "hls" | "mse" | "ytdlp",
  args: {...},
  expect: { tracks: ["video","audio"], minDuration, codecs: ["h264","aac"] }
}
```

纯函数、输入输出都是数据 → 可以写 30~50 条表驱动测试。这是「智能」唯一可测的形态。

**L2-b 输出验证四层**（`downloader.py` 里 `status` 出现 60 次，但「验证产物」这一步不存在）：

1. 文件存在
2. 非空（size > 0）
3. 字节数符合预期（±5%，或等于清单累计）
4. `ffprobe` 能解析出 `expect.tracks` 且时长偏差 < 2s

任一层不过 → 输出明确错误码，**绝不把坏文件当成功**。这条直接治「下完了打不开」。

**L2-c 错误码字典**（**15 个**，每个带阶段/可恢复性/重试预算/用户可读建议）：

```
NET_DNS  NET_TIMEOUT  HTTP_403  HTTP_404        HTTP_429
TOKEN_EXPIRED  SEGMENT_GAP  INIT_MISSING  CODEC_UNSUPPORTED
DRM_PROTECTED  AUTH_REQUIRED  DISK_FULL  VERIFY_MISMATCH
MISSING_DEP  JOB_TIMEOUT
```

> **为什么从 12 一路加到 15**：每次加都是被一次真实失败推着加的，不是凑数。
>
> · `HTTP_429`（1.3.48）：原案没有限速码。2026-10-24 量多连接吞吐时
>   `proof.ovh.net` 单连接正常、4 连接那轮直接吃 429（`ENGINE-EVAL.md` §4-P0）。
>   缺它 →「站点在限速」落进 `NET_TIMEOUT` → 用户看到「连接超时」→ 立刻再点
>   → 被限得更狠。**分类错了，用户的下一步动作就错了。**
> · `MISSING_DEP`（1.3.50）：缺 ffmpeg / yt-dlp。落 `INTERNAL` 等于把
>   「你没装东西」说成「我们写错了」，用户会来报 bug 而不是去装。
>   合并双流时这是最常见的失败。
> · `JOB_TIMEOUT`（1.3.50）：宿主最多等 6 小时。落 `NET_TIMEOUT` 等于把
>   「这个任务卡死了」说成「网络慢」，用户会一直重试同一条地址。
>
> 另有 `INTERNAL` 是**分类器的兜底桶，不属于对用户承诺的原因**：它出现就代表
> 我们漏了一种异常，测试里专门断言「已知异常不许落进 INTERNAL」。

**语义放宽的两处**（写进 `errcode.py` 的注释，因为会影响以后读码的人）：
`DISK_FULL` = 「本地写盘失败」（磁盘满 / 目录只读 / 配额不足，建议一样）；
`NET_DNS` = 「网络层连不上」（解析失败 / 连接被拒 / 需要代理）。

**实现**：`native-host/errcode.py`（纯函数、零依赖）。重试预算**写在码表里**
（`attempts` / `backoff`），不散在 `if` 里 —— 「第几次开始降级」必须是表上的一个数字。
重试对用户**可见**（每次重试前写一条 message），不做静默重试。

**验收**：15 个码每个至少一条测试路径；人为制造 3 种失败（断网 / 删一个分片 / 塞 DRM 清单），popup 显示对应建议。
已做部分：HTTP 路径全部接线（429 重试、403 不重试、5xx 重试、Retry-After 夹取），
HLS / yt-dlp 两条路径 1.3.49 已接完（T-B5 / P3'）：
「同一个原因 → 同一个码 → 同一句话」，三条路的话**逐字相同**；
三条都失败时对外只留最具体的那一个码一句话，三句原话进 `trail` 给诊断包。
第五个入口（`run_merge` 双流合并）与宿主 6 小时超时 1.3.50 也接完了（T-B6）：
合并失败按 ffmpeg 尾巴分类（对不上就 `CODEC_UNSUPPORTED`，因为这一路只做 `-c copy`），
缺 ffmpeg 是 `MISSING_DEP`，超时是 `JOB_TIMEOUT` 且**同步改状态文件**。

### L3 · 工作站：队列 / 续传 / 历史

- 引擎常驻，本地 HTTP（`127.0.0.1` + 随机 token）暴露状态；popup 只做提交与展示。
- 队列持久化（`jobs.jsonl`），**断点续传用 Range**。
- 历史库：每次下载留一条记录（会话摘要 + 验证结果 + 耗时），可检索、可重试。
- 这一层落地后，「关掉标签页就断」和「512MB 内存上限」两个结构性缺陷同时消失。

**验收**：提交 5 个任务 → 关闭浏览器 → 重新打开，引擎侧全部完成且验证通过。

> **2026-10-24 决策（与用户对齐，详见 TODO T-C6）**：本层不再作为整体切片排期。
> 三个能力要分开看：**续传已落地**（1.3.47，P1 指纹），**历史已有**（`chrome.storage.local`
> 跨会话 + popup 记录/重试），**队列**可在现架构内会话内实现（半天量级，不碰安装形态）；
> 真正重的只有「引擎常驻」——而未签名 + 常驻 + 监听端口是杀软高危组合（d-064 实证
> 本机安全软件连 `bin/ffmpeg.exe` 写盘都拦），成本前置、收益频率未量。故「常驻引擎」
> 独立立项挂起 v1.4，触发条件量化（一周内真撞 ≥3 次「想关浏览器但下载没完」）后再做。

### L4 · 知识库双通道（这才是「学习」）

| 通道 | 谁写 | 触发 | 作用 |
|---|---|---|---|
| **解释库**（自动长） | 系统 | 同站点 + 同错误码累计 ≥3 次 | popup 直接显示「已知问题 + 处理建议」。学错只是解释不准，不会下错文件 |
| **规则库**（人工进） | 人 | 用户报告 + 根因 + **可复现测试** 三件齐全 | 才允许新增/修改判定规则。CI 校验「每条启用规则必须有测试引用」 |

`docs/compatibility/NNN-slug.md` 模板：现象 / 复现 / 根因 / 修复 / 测试引用 / 适用版本。
把 `DEVLOG.md` 里 d-047、B6~B11 直接回填成案例——**这些原料你已经有了，只是埋在流水账里**。

**为什么必须分两通道**：漏抓一条只是少一个选项；错抓一条（广告/封面/图标当正文）用户会下错且不自知。代价不对称，所以判定规则必须有人守门。

**该学的是「失败模式」，不是「站点规则」**：失败模式十来个可穷举且十年后仍成立；站点规则无限且会变。

## 6. 必须同时做的产品件（不做这些，技术再强也不像产品）

| 项 | 为什么决定性 |
|---|---|
| **隐私政策** | L1-b 读响应体，商店审核必问。必须写清「只看媒体/播放接口响应、不落盘、可关闭」 |
| **首次空态** | 一进来是空白列表，产品感全在这一屏。给三个动作：在当前页嗅探 / 粘贴链接 / 打开示例 |
| **诊断包导出** | 一键打包「版本 + 错误码统计 + 脱敏日志」。**这是降低支持成本的唯一杠杆** |
| **本地统计（opt-in）** | 不知道失败率就无法改进。默认关，只统计错误码分布与站点域名，不含 URL |
| **发版通道** | Edge Add-ons 优先（审核相对宽松）；Chrome 商店准备被问 DRM |
| **法律声明** | 「仅用于你有权访问的内容，不含 DRM 绕过」。不出现 YouTube 示例，不写「支持某站会员内容」 |
| **i18n（zh + en）** | 想被非中文用户用，这一条是门槛而不是加分 |

## 7. 明确不做（省下的时间比新增功能更值钱）

- **订阅 / 批量下载某 UP 主新视频**：政策风险最高，且把产品从「个人备份」变成「内容搬运」，直接踩商店红线。
- **任何 DRM 绕过**：不做，且要在文档里明确不做，这是护城河而非短板。
- **0.92 那种小数置信度**：没有标注集就是装饰。用 `strong / weak / conflict`。
- **AI 在线诊断**：给还没有稳定 oracle 的系统加解释层，产出的是「自信的错误解释」。
- **移动端 / 云同步**：与「本地优先」的核心主张冲突。

## 9. 最先要你点头的一个决定（已完成：1.3.52 双跑接线）

**S0 做不做「双跑并行」**。它会让 S0 从 2 天变成 3 天，看起来是浪费；但它决定了后面五层是「渐进替换」还是「一次性重写」。一次性重写在这个仓库的历史上有过教训（B7 交自动化测试全绿、真机两条全废，靠 B8 返工）。

## 10. 第二阶段：智能化——从「告诉你为什么」到「学着解决」（2026-10-24 定案）

> 一句话定位的演进：§2 说「下不下来时告诉你为什么」。第二阶段给它加上后半句：
> **「然后开始学着解决」**。用户原话：「我想要一款智能狗狗，但它现在只是一个玩偶。」
> 定案结论：方向没有找错，**缺的是大脑，不是骨骼**——验证四层、错误码表、诊断包、
> 回放测试、失败签名，这些正是任何可信智能体都需要、而市面产品普遍没有的
> 「可观测性 + 行动验证」。第二阶段的全部工作 = 在这个确定性内核上，装大脑。

### 10.1 目标形态

未覆盖的失败 → **大脑分析**（结构化诊断 → 根因假设 + 候选动作）→ **受限尝试**
（扩展执行、产物过验证四层、N 轮上限）→ **经验沉淀**（成功策略 → 候选规则 →
回放验证 → 码表与规则库生长）→ 下次同类失败直接命中。

### 10.2 四条原则（继承既有纪律，一条不让）

1. **智能骑在确定性内核上**：智能层提议的一切动作，产物必过验证四层——
   这是本项目区别于「AI 乱来」产品的护城河，第二阶段不许拆；
2. **经验入库必过回放**：规则库准入从「人工守门」升级为「测试守门」——
   候选规则必须在历史案例回放中通过；
3. **语料 ≠ bug 报告**：采集的失败只做训练数据，产品问题仍由日常使用与测试发现
   （d-047 的「假 bug 洪水」教训）；**纯度 > 数量**；
4. **不重写**：CLI 老路保留为兜底；yt-dlp 的站点知识继续借社区的，
   自己拥有的是驱动层与插件层。

### 10.4 边界

- **隐私**：打磨期不设限（LLM 用用户本机配置的 key，失败诊断出网）；
  发行前收成 opt-in 开关——设计上诊断内容白名单化，回收是设置项不是重构；
- **码表是活的**：15 → 16 → 17 的生长靠 M1 语料的 INTERNAL 桶归纳
  （LLM 提议新码/新规则 → 回放验证 → 入表）；
- **不做的**：微调/训练模型（数据量级不够，收益不如评测集+经验库）；
  全自动无守门进化（违背原则 2）。
